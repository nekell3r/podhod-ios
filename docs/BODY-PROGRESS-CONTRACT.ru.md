# IOS-08: личные замеры и фотографии

Пользователь поручил самостоятельно реализовать оставшийся бэклог без дополнительных вопросов. Для личных фотографий выбирается локальное приватное хранение: серверный API и публичное объектное хранилище не добавляются. Синхронизация тренировок не должна создавать впечатление, что эти данные загружены в аккаунт на сервере.

## Данные и границы

- Отдельный `body-progress.json` v1 в текущем `AccountWorkspaces`; фотографии — в соседнем каталоге `progress-photos`, имена только из UUID. Тренировочный архив, питание и их API не меняются ради замеров.
- Замер имеет UUID, дату, сохранённый timezone и явно заданные значения. Метрики: вес в кг; талия, грудь, бёдра, левая/правая рука, левое/правое бедро, левая/правая голень в см. Отсутствие не равно нулю. Значения конечные, вес `(0,1000]`, окружности `(0,500]`; это технические ограничения ввода. По одной записи на календарную дату; изменение уже существующей даты открывает её запись.
- Фотография имеет UUID, дату/timezone и ракурс `front/side/back/other`; дата задаётся пользователем, а не извлекается из EXIF. Запись замера не обязательна для добавления фотографии. До 5000 дат замеров и 500 фото; длинные архивы не пересчитываются при каждом вводе поля.
- Даты — 1900–9999. Графики строятся только по измеренным значениям выбранной метрики, неизвестные не интерполируются как ноль. Сравнение фото требует явного выбора двух собственных снимков; приложение не генерирует «до/после» и не делает медицинских выводов.

## Приватность импорта

Выбор — штатный [Photos picker](https://developer.apple.com/documentation/photokit/bringing-photos-picker-to-your-swiftui-app) с доступом к выбранному снимку. Не запрашивать всю медиатеку ради импорта и не сохранять ссылку, позволяющую позже перечитать другой оригинал. Отмена/ошибка импорта оставляет архив без изменений.

Импорт создаёт ориентированную JPEG-копию с длинной стороной до 2048 px через новый пиксельный буфер sRGB. Исходные GPS, EXIF, имя и прочие метаданные в копию не переносятся. Кодировщик ImageIO добавляет собственные технические поля: допускаются только `PixelXDimension`/`PixelYDimension`, совпадающие с итоговыми пикселями, `ColorSpace=1` и обычные сведения JPEG/sRGB. Комментарии, даты съёмки, координаты и сведения камеры не допускаются. Технические границы — до 50 MiB входных данных, 100 мегапикселей и 8 MiB подготовленного JPEG. Декодирование/подготовка выполняются вне главного потока, один импорт за раз. Перед сохранением проверить отмену и актуальность рабочего каталога; поздний результат старого экрана не записывает фото в другой аккаунт.

Архив и фото находятся в [Application Support](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html), с [FileProtectionType.complete](https://developer.apple.com/documentation/foundation/fileprotectiontype/complete) на iOS. Они не находятся в Caches, общем каталоге Files или bundle. При уходе приложения в фон содержимое экрана скрывается от снимка переключателя приложений. Никаких фоновых загрузок на сервер, аналитики изображений или общих URL.

## Запись, удаление и восстановление

Новая картинка получает новый UUID и сначала записывается в приватный каталог, затем атомарно сохраняется manifest. При ошибке manifest удаляется только созданный этой операцией файл; исходные данные не меняются. Прерванный импорт может оставить невидимый лишний файл: он не должен появляться в интерфейсе или удаляться массовой очисткой.

Удаление фото подтверждается. Manifest атомарно удаляет видимую запись и сохраняет UUID в журнале ожидающего удаления; файл удаляется по этому UUID, затем журнал очищается. При сбое удаления журнал остаётся для повторной попытки и интерфейс сообщает о незавершённой операции. Удаляется копия текущего рабочего каталога; оригинал в системной медиатеке и прежние резервные копии не изменяются. Это значение действия должно быть видно пользователю.

Неизвестный/повреждённый формат manifest не заменяется пустым. При изменении формата сохраняется исходный файл перед первой записью. Отсутствующий файл отдельного фото показывается как недоступный снимок с возможностью явного удаления записи; остальные замеры не теряются и файл не подменяется другим изображением.

## Аккаунты и backup

Гость и каждый аккаунт получают свои manifest и каталог фото. Выход не удаляет записи аккаунта; при входе другого пользователя они не отображаются. Перенос гостя включает оба ресурса, сохраняет исходники и восстанавливается после прерывания только при совпадении уже скопированных данных. После принятия гостя каталог гостя ротируется. Автоматического слияния с существующим аккаунтом нет.

`workspace.json` переводится в v2 с точной резервной копией v1. Маркер `legacyWorkspace` сохраняет исходное расположение старого архива до штатного переключения. Старый клиент не должен открывать v2. Перед копированием создаётся `guest-adoption.json` с UUID переноса, исходным гостевым каталогом и хешами файлов. Подтверждение UUID переноса и ротация гостя записываются атомарно в selector. Незавершённый перенос от прежнего гостя сохраняется в отдельной резервной копии перед удалением только доказанно созданных им файлов; посторонние изменения блокируют переключение. Завершённый перенос с подтверждением не откатывается при сбое удаления журнала.

Подтверждённый `/v1/profile` subject сохраняется вместе с конкретными OAuth credentials в Keychain, сохраняется при refresh и не переносится в новый вход. После перезапуска приватный архив открывается офлайн только при совпадении подтверждённого subject и текущего рабочего каталога. До первого подтверждения нового входа или при переключении прежний store закрыт; поздние результаты импорта не принимаются. Снятие блокировки устройства не отменяет это ограничение.

Резервирование/перенос не должны загружать все изображения в память одновременно. Системная резервная копия устройства может содержать приватные файлы приложения согласно настройкам iOS; её наличие и восстановление не обещаются по одной сборке или Simulator-тесту. UI явно сообщает: «Только на этом iPhone» и о зависимости восстановления от резервной копии устройства. Ручная отправка фото и облачная синхронизация не происходят автоматически.

## Проверки перед выпуском

Core: числа/даты/дубликаты, отсутствие вместо нуля, неизменность других дат, сохранение/перезапуск, неизвестный файл, UUID/path traversal, ошибочная запись manifest, журнал удаления, отсутствующее фото, перенос гостя и изоляция аккаунтов. ImageIO: синтетическая картинка с GPS/ориентацией, ограничение размера, отсутствие GPS после импорта. UI: один headless iPhone 15, синтетические замеры и два искусственных снимка, добавление/график/сравнение/подтверждённое удаление. Не использовать реальные фотографии пользователя для автоматических тестов.

Физическая блокировка, системное резервирование/восстановление и поведение Photos/iCloud на реальном iPhone отмечаются отдельно; они не подтверждаются core-тестами или скриншотом Simulator.
